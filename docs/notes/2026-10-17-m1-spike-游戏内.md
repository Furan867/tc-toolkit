# M1 spike：自研产物在游戏内跑通（2026-10-17）

## 结论

**自研 blob 在游戏进程里被 JIT 执行了，游戏没崩。** 这是 M1 的收尾判据。
（"跑通空程序" = 产物能过游戏的全部校验与执行路径；它不是能驱动仿真的程序 —— 那要等前端。）

## 步骤（可重跑）

1. `python tools/deploy_compile_hook.py build-deploy`（游戏必须先关：DLL 有文件锁）
2. 生成 spike 产物：`build/tcblob.exe --obj build/objs/rt_min.o --obj build/objs/entry_shim.o
   --obj build/objs/prog_empty.o --entry __tc_entry --out build/blob_empty.bin`
   → 728 字节，sha256 `3b378baa5c12f287c8b3d46d42be186e3d5d4c58fdffb325839612ff2c777472`
3. `opt.ini` 里 `compiler = ours`（**不用重新部署**，壳每次编译都重读该键）
4. **用 `reference` 启动游戏**，跑起来之后再切 `ours` —— 别带着 `ours` 启动（见下「踩到的坑」）
5. 触发一次编译：`python tools/simctl.py recompile`（注入 Ctrl+Z；需要有编辑历史）
6. 验证（四条，全部实跑过）
7. 恢复：`opt.ini` 改回 `compiler = reference` + 再触发一次编译

## 证据（2026-10-17 12:24:34，游戏 PID 15856）

| 判据 | 结果 |
|---|---|
| `work/hook/manifest.tsv` 新行 | seq 006、`impl=ours`、`out_len=728`、`out_sha256=3b378baa…`（= 我们的 blob） |
| `work/opt/hook.log` | `006 impl impl=ours result=ok` |
| **`work/tmp/blob_ran.log`** | `blob ran, tag=23063` —— blob 里 `tc_spike_mark` 写的一行，证明**我们的代码真在游戏进程里执行到了那一步** |
| 游戏进程 | PID 15856 存活；`SendMessageTimeoutW(WM_NULL)` 2 s 内有应答（没卡死） |
| 崩没崩 | Windows Application 日志近 3 小时**无** Application Error / WER 事件 |

bit62 的间接证据：游戏用完产物后会走 `eqdestroy` 的门控，头里没置 bit62 就会拿 Nim 的分配器去 free
我们的 `malloc` 指针 —— 那会崩；没崩说明门控按预期走了「不 free」。

## 踩到的坑

- **别带着 `compiler = ours` 启动游戏**：启动时会编译「地图电路」（39750 字节），拿到什么都不做的程序后
  地图构建不出来，表现为**游戏起不来**（第一次实测就是这样，误以为崩了；查 Application 日志才确认没崩）。
  正确姿势是先用 `reference` 起来，再热切 `ours`，而且只在小电路上触发编译。
- `simctl.py recompile` 是**消耗性**的（Ctrl+Z 撤销）：撤销栈空了就静默无效（这次恢复时 `--redo` 就没触发编译）。
  恢复要靠负责人自己在游戏里编辑一次。
- COFF 的 `REL32` **addend 是有符号的**（GCC 用 `-1` 做字面量地址偏置）—— 见 `docs/facts.md`，
  这个 bug 是在给 blob 加「可观测标记」时才暴露出来的（多了字符串引用才踩到）。

## 为什么标记必须只用 kernel32 + 纯算数

`rt_min.cc` 会被链进 blob，任何 CRT 符号（`sprintf` 之类）都是 `ExternResolver` 解析不了的未定义符号。
`tc_spike_mark` 因此手写十进制转换，只调 `CreateFileA`/`WriteFile`/`CloseHandle`
（它们经装配器的 `__imp_` 指针槽 + 壳的 `GetProcAddress` 落到真实 kernel32）。
