# M1.5 收益探针：006 的 clang -O2 等价物 vs 参考产物（2026-10-17）

## 结论（先看这个）

1. **正确性：逐 tick 全等**。`006.si` 的 clang 等价物（两个变体）对参考产物 **10/10 tick、
   页哈希/状态字段/extern 逐条相同**，白名单**一条都没有**（`page_whitelist = {}`）。
   两遍 host 的原始快照：`simplexc/probe/results/006_{fold,hot}.{ref,ours}.jsonl`。
2. **吞吐：宿主机里量到的「收益」取决于写法，而且量到的绝对值被宿主自己的开销主导**。
   N=10 亿 cycle 的同驱动对比（同一 N → 同一个爆发次数 k → 每爆发开销 a·k 在差里直接消掉）：

   | 变体 | 每 cycle（T/N，含 a·k/N≈0.4 ns） | 相对参考 | 静态（整份 blob） |
   |---|---|---|---|
   | 参考产物 | **1.36 ns** | 100% | 3090 条指令 / 13069 B |
   | 我们的（fold，忠实直译） | **1.74 ns** | **128%（慢 28%）** | 517 条 / 2164 B |
   | 我们的（hot，热计数器进寄存器） | **0.47 ns** | **34.6%（快 2.9×）** | 551 条 / 2292 B |

   → **收益不在「把源码直译成 C 再交给 clang」这一步，而在降级层/前端把热状态留在寄存器里。**
   直译版本连参考都打不过（原因见「机制」），`hot` 只改了一处（每周期计数器先提到局部变量、
   循环结束再写回全局，语义完全一样）就从 0.78× 变成 2.9×。
3. 006 太小：宿主驱动下**每 tick 只推进 1 个 cycle**，所以「每 tick 墙钟」这一栏（两边 ~5 ms/tick、
   比值 98~104%）量的是宿主的轮询粒度，不是电路。真实收益量级必须由**游戏内**那一枪定
   （主程持 game.lock 做），本探针只给「同驱动、同 tick 语义」下的相对结论与一条机制线索引。

## 判据入口（可重跑）

    python simplexc/tools/probe_006.py                      # fold（默认）
    python simplexc/tools/probe_006.py --variant hot

逐 tick 差异清单与白名单、每个量测点的 5 轮原始秒数 + pacing 计数 + `sim_cycle`、拟合残差。

## 从参考产物实验出来的 006 语义（这些是结论，别重猜）

1. **`Time` 的单位是纳秒**（不是毫秒），`33.ms()` = 33 000 000（ns），`1.ms()` = 10^6 ns。
   - 旁证：产物里那句 `nanos_per_cycle`、`speed = min(ctl_cycle_speed_ms, 10^13)` 的注释
     「Cap at 10 ghz」（speed 是 Hz；`get_target_cycle` 的结果 = t·10 = 10 GHz 的周期数）。
   - 实测：把 33 当纳秒用（我第一版），`burst_cycles` 被钉在 1 —— 目标 2000 个 cycle 要
     **2000 次爆发**（时钟回调 63 → 2002 次，12 ms → 408 ms）；改成 33e6 后爆发次数
     与 √(2N) 模型逐点吻合（k(N) 实测 = 模型值：1414/4472/14142/44721）。
2. **参考产物每个 tick 只推进 1 个 cycle**：宿主把 `sim_target_cycle` 设成 1..N，
   程序跑到 target 就停；所以「宿主驱动的每 tick 墙钟」≈ 宿主自己的采样粒度。
3. `#if in_scope("get_input"/"check_output"/"on_ui_update")` **三处都不生成代码**
   （旁证：参考产物每次爆发只有 1 次时钟调用、每 cycle 无任何 call；`on_manual_input`
   块里的函数在 006 里根本没定义，装进 scope 会编译不过）。所以 `level_input` 恒为初值 0，
   `input_replay[0]` 每周期写 0，`level_output` 只在程序自己的 .bss 里。
4. `mode_refresh()` 从**内存**回读刚写的两位再算 NAND（不是用局部变量），所以最终
   `SIMULATION_STATE[256..261] = 0,0,0,0,1,1`（两遍逐字节一致）。
5. `reset_sim()` 里的 `global_seed = Seed(...)` 落在 DLL 的 .bss（宿主不比对那块）→ 没复刻；
   006 不用随机数。`memory_clear` 的三段（8192/8192/263）照写零。
6. 收尾路径：`quit_simulation` → 程序根返回 → 宿主 `close()` 报 `exited_clean`（两边一致）。

## 机制：为什么「忠实直译」反而比参考慢 28%

- 我们的内层环 5 条指令：`mov [input_replay],0` / `mov rax,[cycle]` / `inc` / `mov [cycle],rax` /
  `cmp+jl` —— 计数器 `cycle` 在内存里绕一圈（store→load 链 ≈ 5 cycle/周期）。
- 原因：游戏内存是 `volatile`（天道：游戏别的线程会改命令块），而 `cycle` 是 u64 全局，
  LLVM 必须假设 `volatile u64` 的写**可能命中** `cycle` → 不敢把它提到寄存器。
- 把计数器先提到局部（`hot` 变体，循环体内无人读 `cycle`，语义等价）后：**0.47 ns/cycle，
  比参考快 2.9×**，且逐 tick 仍然全等。
- 对 M3 的可操作结论：游戏内存的访问需要「有序但不与私有状态别名」的语义
  （独立 address space / `__restrict` 式的见证，或把私有热状态放寄存器并显式定序）。
  照抄「全部 volatile」会把收益全吃掉。

## 宿主侧：extern 跳板清单（stub sidecar，接口冻结版 1.1 增量）

- `assemble.hh` 新增 `struct StubRef { uint64_t offset; std::string symbol; }` 与
  `AsmResult::stubs`（offset 相对机器码起点，顺序 = 造桩顺序，纯增量）。
- `cli/tcblob.cc` 装配成功后写 `<out>.stubs`（TSV：`offset<TAB>kind<TAB>symbol`，offset 十六进制小写）。
  kind 由符号名决定：`__imp_*` → `slot`（8 字节数据槽），其余 → `stub`（12 字节代码桩）。
- `tools/host/host.py`：`<bin>.stubs` 存在时读它 —— ① 这些 offset 上的 movabs 不再触发
  「地址表外 + 已映射」硬错误（它们本来就是产物自己的跳板）；② 按符号（去掉 `__imp_`）查 detour 表，
  命中就把 imm64（offset+2）/ 槽内容改成宿主桩地址，**走与 IAT 槽完全同一条 handler 与记录格式**，
  两边的 extern 序列因此可以直接逐条比；③ 未命中 → 打印符号名并以退出码 3 退出（宁可吵）；
  ④ sidecar 说有的 `stub` 却在那个偏移找不到 `movabs` → 也报错（编 3）—— 那说明 sidecar 与产物不是一对。
  统计进 `stats["stubs"]/["slots"]`。
- 006 的 6 处：`stub Sleep`、`stub GetSystemTimePreciseAsFileTime`、4 个 slot
  （`__imp_{ExitThread,CreateFileA,WriteFile,CloseHandle}` 来自 `rt_min.o`）。
  `CreateFileA`/`CloseHandle` 原来没有宿主桩（rt_min 的 spike 记录器带来），本批补了两个
  一律失败的桩：否则按契约「未命中即报错」，而真开文件会把真实时间/磁盘引进两遍跑。
- sidecar 是宿主**唯一**知道「哪些 movabs 是跳板」的来源：没有它，`kernel32` 的绝对地址会被
  当成未知地址拒跑（实测就是这么被挡住的）。

## 噪声与局限（别把这里的数字当游戏内结论）

1. 宿主把 `Sleep`/时钟换成了 Python ctypes 回调，**每次回调要抢 GIL**：实测每次爆发
   （= 每个时钟调用）≈ 8 µs；一次 run 的回调次数 k ≈ √(2N) → 大 N 下「每次爆发开销」仍是
   每 cycle 0.4 ns 的量级（占了参考 T/N 的 30%）。配对差与 T/N 把这一项消掉了，绝对值没有。
   `sys.setswitchinterval(1e-6)`（量测子进程里设）只把最坏尾巴削掉一点。
2. 拟合 `T = c + a·k + b·N` 的 `a/b` 会互相分配（`hot` 解出 b = 0.12 ns/cycle，物理上不可能：
   一圈至少 1 cycle ≈ 0.3 ns）→ **拟合 b 只作参考，头条用配对差/T/N**；原始点、5 轮秒数、
   残差都在结果 JSON 里。
3. 每 tick 只有 1 个 cycle（见上）→ 「每 tick 墙钟」这一栏没有电路信息，只有宿主粒度。
4. `fold` 变体的内层体被 clang 常量折叠（输入恒 0、输出没人读）；`nofold`（`-DTC_006_NO_FOLD`
   给电路状态加 volatile）本批**没跑** —— 想量「同样的每周期工作量、不同代码质量」就把它跑上。
5. 只在宿主里验过；游戏内（真 Sleep、真时钟、游戏设的 target_cycle）待主程持锁验。

## 工具链：clang.exe 怎么来的

- `tools/fetch_llvm.py` 加了 `--extra bin/clang.exe`（可重复）与 `--offline`：
  离线重解只用本地压缩包 + 上次 `llvm.json` 里记的 sha256（GitHub 匿名 API 有额度，用完 403）。
  顺带修了一处老 bug：`releases/{ref}` 只对 `latest` 合法，按 tag 查必须 `releases/tags/<tag>`
  （原来 `--tag llvmorg-23.1.3` 一直 404）。
- 判据：删掉 `build/llvm/bin/clang.exe` 后
  `python tools/fetch_llvm.py --offline --tag llvmorg-23.1.3 --extra bin/clang.exe` 重解出来，
  sha256 = `9584244d83bb095c5a2983f814692cb50e0b8d2916585516cad8f3e8596d8261`；
  `clang --version` = `clang version 23.1.3 (https://github.com/llvm/llvm-project 0d261d1ca552c95a8f007e061c787ac7132fbcbc)`。
  压缩包 sha256（记进 llvm.json 并校验）= `7e69dc07…ba01d`。

## 未解 / 下一步

- 参考产物的**热环**没定位到：实测 b_ref ≈ 1.0 ns/cycle（≈3 个周期/周期），静态上找不到
  明显相符的环（候选 0x2a44 那圈 32 条指令若真在跑就是 >10 ns）→ 要么还有别的环，要么
  那个环被游戏编译器化简过。要定位得做动态（RIP 采样）而不是猜反汇编。
- 006 的 `get_input`/`check_output` 若在某些捕获里**在 scope 内**，每周期会多一次调用，
  收益结构会完全不同 —— 需要一个「输入真的在变」的电路再来一轮。
- 白名单机制目前是空的（全等）；等出现「UI/error 文本地址不同」那类电路再用它，
  格式已定：`PAGE_WHITELIST = {页地址: 理由}`，逐条写进结果文件。
