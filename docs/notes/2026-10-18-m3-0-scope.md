### 3.1 为什么这些只能做实验，不能读反汇编

TSV 里 `experiment` 列全是「最小 `.si` + 驱动命令 + 看哪个页/字段」，统一四步：

1. 把该构造抄成最小 `.si` 片段（写 `#SIMULATION_STATE + k` 这几个可观测偏移）；
2. `python tools/try_compile_dll.py --compile --src <frag>.si` —— **必须子进程**（解析期断言会 fatal 整个进程，§7.1）；
3. `python simplexc/tools/host/host.py --src <frag>.si --bin <ref>.bin --ticks N --dump-pages <dir>`；
4. 看页/偏移的字节、`error_buffer` 的长度头与编码、`ctl_*`/`sim_*` 字段、extern 桩记的实参序列。

不靠反汇编的四条理由：

1. 参考产物是 ~46600 条扁平指令、无符号无类型：`load(<U5>,p)` 与「按字节读再掩码」在反汇编上是
   同一条 `movzx`+`and` 的两种排法，**分不出语义来源**。
2. 语义是可观测**状态**（对内存的写），同一语义有多种指令形状（`mov [mem],eax` vs 先清高位再写 8 字节），
   所以判据只能是逐 tick 页哈希，不是指令形状。
3. 有些问题不属于产物内容：`#if in_scope`、不可达函数——产物里缺一段代码既可能是「没生成」
   也可能是「生成了被 DCE」，只有「源码有/无那一块」两次编译对比才能定（§7.1 就是这么定下来的）。
4. 反汇编看不到 extern 的实参与返回值序列，而恰恰是那串序列给出了 `Time` 单位、短路记账顺序这类结论
   （反面：节奏类调用 `sleep`/`get_time` 不能进可观测序列，facts.md:287）。

**怎么读 `experiment` 列（诚实的边界）**：L1/L3/L4/L5 的 78 条给的是**具体片段名 + 观测点**；
L2 的 62 条给的是**统一配方**（“把该组件的 refresh/run 片段抄成独立 `.si`，看它写的那几个
`#SIMULATION_STATE` 偏移”）—— 逐个 kind 写 62 份最小 `.si` 属于 M3.0 实验清单的**落地工作**，
本任务只把方法、观测面与载体（`try_compile_dll` + `host --dump-pages`）钉下来。

## 4. 判据 4：构造 → LLVM IR 映射草图（抽查 4 条，含风险点）

内置的 IR 草图写在 TSV 的 `ir_sketch` 列（每条一行）。这里展开 4 条最关键的，
API 名都对着 `build/llvm/include/llvm-c/Core.h`（LLVM 23.1.3）核过。

**(a) `load` / `store`：地址单位是地基（§9 U-L1，未定）**

```
; Simplex: store(#SIMULATION_STATE + 264, U32 (value_id264))
%addr = add i64 <state_const>, 264                  ; LLVMBuildAdd
%p    = inttoptr i64 %addr to i32*                  ; LLVMBuildIntToPtr
store i32 %v, i32* %p, align 4                      ; LLVMBuildStore + LLVMSetAlignment

; Simplex: load(<U8>, p) → U8
%q = inttoptr i64 %addr to i8*                      ; LLVMBuildIntToPtr
%v = load i8, i8* %q, align 1                       ; LLVMBuildLoad2(i8_ty, q)
```
必须**直映射**成 LLVM `load/store`，不能降成 runtime 调用（主设计 §5 第 1 条：语料里 9.4k 处 load/store）。
未定的两点写死在 lowering 里之前必须做实验：**地址单位**（`p + 1` 是 +1 字节还是 +1 元素）、
**非字节宽度**（`load(<U5>, p)` 是先 `load i8` 再 `trunc`/`and 0x1f`，还是 `i5*` 直接读）。两种 IR 都写得出，
选哪个只能靠实验 —— 理由见 §3.1 第 1/2 条。

**(b) U32 截断与位宽提升（§9 U-L7，未定）**

```
; Simplex: U32 (U64 x)      → 窄化
%t = trunc i64 %x to i32                            ; LLVMBuildTrunc
; Simplex: U64 u32v         → 变宽（无符号 → 零扩展）
%z = zext i32 %u32v to i64                          ; LLVMBuildZExt
; Simplex: U1 (U32 x)       → 到 i1
%b = trunc i32 %x to i1                             ; LLVMBuildTrunc（等价于 & 1，但语义要说清）
```
**风险点就在这里**：这份源码里有 16 种位宽（U1…U64 + S32），其中 7 种是非 2 的幂（U3/U5/U6/U7/U10/U12/U20/U24/U27/U33）。
LLVM 里 `LLVMIntType(ctx, 33)` 合法，但**后端不会保证 33 位运算的截断语义与参考实现一致**；
参考实现是「按位掩码」的软件语义。最稳的写法是把非 2 的幂宽度在 lowering 里展开成
`i64 运算 + LLVMBuildAnd(掩码)`（掩码宽度由实验定），而不是交给 `i33`/`i5` 让后端猜。

**(c) 嵌套 def 的闭包捕获（§9 未列，我列为最险的一条）**

```
; 外层 mode_run 里的 var：burst_target_cycle / halt_run / original_start_time / speed …
%burst_target_cycle = alloca i64      ; LLVMBuildAlloca（提到函数入口块，不用 alloca 在循环里）
%halt_run           = alloca i1
; 内层 def halt → 独立 LLVM 函数，捕获变量按**引用**传（隐式指针参数）
define void @mode_run$halt(ptr %burst_target_cycle, ptr %halt_run, i64 %cycle_now) {
  store i64 %cycle_now, ptr %burst_target_cycle ; LLVMBuildStore
  store i1 true, ptr %halt_run
  ret void                                      ; LLVMBuildRetVoid
}
```
`halt` 读的是**全局 `cycle`**、写的是外层的 `burst_target_cycle`/`halt_run`；
`handle_test_result` 还读 `max`/`set_setting`；`get_target_cycle(time_now)` 捕获
`original_start_time`/`orig_start_cycle`/`speed`。捕获是**值捕获还是引用捕获**决定了 IR 形状
（值捕获要额外写回），必须实验（`closure_capture`，TSV 里有配方）——
这条比 (b) 更险，因为它同时影响协议循环的**控制流**（`halt_run` 决定外层 while 退出），
一旦语义搞错不是数值差一点，是死循环或提前退出。

**(d) 组件模板（96% 的代码行）**

以最常见的 `com_static_indexer` 为例：

```
; Simplex: let value_id384 = (U32 (load(<U1>, #SIMULATION_STATE + 354)) << 31)
%b   = load i1, i1* %p354                 ; LLVMBuildLoad2(i1_ty, …)
%e   = zext i1 %b to i32                  ; LLVMBuildZExt
%s   = shl i32 %e, 31                     ; LLVMBuildShl
; 两句 store（写同一个值到两个偏移）不合并 —— 参考产物就是两次写，页哈希只看最终值，
; 但中间态可能被 extern（halt/sleep）观察到，别自作聪明省一次写
```
模板里还有「读-改-写位域」（`vid \|= v` / `and_field \&= v`：`load→Or/And→trunc→store`）和
「动态地址 store」（`#SIMULATION_STATE + N + Int (min(7, x) * 8)`：`LLVMBuildAdd` 到
`inttoptr` 再 store）。**这一层没有新的 IR 概念，只有排列组合** —— 所以 M3.0 的 IR 生成器
可以按「表达式树 → 指令序列」的一条通道做完，不需要为每个组件写专用 lowering。

## 6. 接口缺口（本任务**不改**接口文档，只列出）

**缺口 1：分析范围 ≠ 整个文件（需要写进 frontend/README，不是改冻结接口）**
实测（§7）：参考实现只分析**可达闭包** —— 未调用的 `def` 体里有未定义名、类型错、括号不匹配都照样出产物。
接口 §1 的 `parse_and_typecheck(src)` 与 §8 的「未支持构造一律 `CompileError`、禁止静默降级」，
按字面理解会把这份源码判为「不支持」（`rv32im.si:154` 的括号错、死代码里的 `'内存'`、`@Size`）。
**建议的收口**：把「不可达 def」定义成**只跳过、不报错**，并在 `TypedProgram` 里记一份
`skipped_functions[]`（给覆盖率矩阵与回退率统计用）——这样 §8 的「不静默降级」仍然成立（有记录、可审计），
而且与参考实现的行为一致。**这是需要负责人拍板的一条**（改的是纪律的解释，不是接口字段）。

**缺口 2：`'…'` 单引号字面量的语义（§9 U-L3 未定）**
`rv32im.si` 只在这 8 行用（`get_ram_value`/`set_ram_value` 里比 `label == '内存'`），**全是死代码**。
→ M3.0 不需要语义，但**词法器必须先能吃掉它**（否则死在词法层，连跳过都做不到）。

**缺口 3：`load(type_of(size), p)` 这类「类型由值决定」的 load（§9 U-L11 未定）**
接口 §1 有 `TypeKind::TypeValue`，所以**表示上不缺**，缺的是语义规则（`type_of(x)` 对值还是对类型、
`@Size` 实例化后是不是常量）。同样只在死代码里出现 → M3.0 记录为「不支持但可跳过」，
路线 A（编译前缀）时必须补。

**缺口 4（不是接口问题，是靶子的问题）**：`rv32im.si:154` 括号不匹配。
参考实现遇它是断言级 fatal（`front_end.nim(2688) Missing open paren`），只是因为该函数不可达才没炸。
这给了 M3.0 一个必须明确的行为：**跳过函数体时不能做表达式级解析，只能按花括号配平扫过去**。

## 7. 本次做的两个实验（可重跑，日志在 `work/tmp/dossier/`）

### 7.1 def 体是「按需分析」的（决定 M3.0 的范围）

```
$ python tools/try_compile_dll.py --compile --src work/tmp/dossier/exp_paren/uncalled_undef.si
  [0] 0x0000000000002185   ← 8581 B（= facts 里「只定义函数」的产物大小）
  [2] 0x000000000000212F   ← entry
  [3] 0x0000000000000000   ← 无错误
$ python tools/try_compile_dll.py --compile --src work/tmp/dossier/exp_paren/called_undef.si
  [0] 0x0  [3] 0x000000000000000D   ← COMPILER ERROR（13 字节错误消息）
```

| 最小片段 | 内容 | 结果 |
| --- | --- | --- |
| `uncalled_undef.si` | `def f() Int { return zzz_undefined_name }`（不调用） | rc=0，8581 B，`out[3]=0` |
| `called_undef.si` | 同上 + 顶层 `f()` | `COMPILER ERROR`（`out[3]=13`） |
| `uncalled_typemismatch.si` | `def f() Int { return "x" }`（不调用） | rc=0，8581 B |
| `bad.si` | 死代码里多一个 `)` | rc=0，8581 B |
| `live_bad.si` | 同一个函数 + 顶层调用 | **rc=1，进程 fatal**：`front_end.nim(2688, 28) 'false' Missing open paren` |
| `ctrl_missing_arg.si` | 被调用函数里 `store(Ptr 4096, )` | `out[3]=0xD` → 返回错误 Result（不 abort） |
| `brace_bad.si` | 花括号不配平（后续顶层语句被吞） | `out[3]=0xD` → 错误 |
| `control_store.si` | 顶层 `store(...)` 一句 | 8594 B（8581+13 → 证明顶层语句确实进产物） |

→ 结论：**语法/语义分析按可达性按需进行；花括号配平是文件级结构要求**。
`live_bad` 与 `ctrl_missing_arg` 也顺带说明：参考实现的错误处理**分两层** ——
解析期的断言会 fatal 整个进程（拿不到 Result），类型/参数错误才返回 `out[3]≠0`。
壳的熔断（VEH + 超时）必须把前者当「ours 失败」处理，不能指望 Result。

### 7.2 宿主目前跑不了这个靶子（M3.0 判据的前置阻塞）

```
$ python simplexc/tools/host/host.py --src simplexc/corpus/rv32im/rv32im.si \
      --bin simplexc/corpus/rv32im/rv32im.bin --entry 0x215B --ticks 10 --out …
[host] 异常 code=0xC0000005 addr=…+0x2389  params=[0, 1688460394496]    ← 读 0x18920150000，rc=3
$ python simplexc/tools/host/simspec.py simplexc/corpus/rv32im/rv32im.si
标量地址 9 个，数组 2 个，跨度 0x188B5190000..0x188B8930000            ← 少了整批 #DATA_*/#RESET_DATA_*/#SETTINGS_*
```

根因（读代码得到，一行）：`simspec.py:16` 的 `PTR_RE` 以 `\s*$` 结尾，
而生成器给这批常量都加了**行尾注释**
（`const #RESET_DATA_7069020504170261741 = Ptr 1688460396544 // """ & $(c_alloc(...) + 2048) & ..."""`）
→ 这批地址进不了地址表 → `game_lo/game_hi` 区间偏窄 → 产物里对
`#RESET_DATA_… - 2048`（= 0x18920150000，正好是页基址）的读落在未映射页 → AV。
`reset_sim()` 里 `memory_copy(#RESET_DATA_… - 2048, #DATA_… - 2048, 134221824)` 是每个 tick 都要走的路径，
所以**这必须在 M3.0 动前端之前修掉**（改 `simspec.py` 一条正则，或宿主加「按行尾注释容忍」；
归属在工具侧，不在编译器侧）。修完后建议先跑「参考 vs 参考 10 tick，差异 0」当基线。

## 8. M3.0 验收判据草案

判据入口（**待建**，主程决定放哪儿；下面是形状）：

```bash
# 0. 覆盖率自证（本文件已过）
python work/tmp/dossier/coverage_check.py                     # 期望末行 PASS

# 1. 编译：我们的编译器吃这份 .si，出 blob + entry
python simplexc/tools/cli_run.py --src simplexc/corpus/rv32im/rv32im.si \
       --out work/tmp/m3/rv32im_ours.bin --entry-out work/tmp/m3/entry.txt
#    期望 rc=0；blob 头 8 字节 = out_len | (1<<62)；out_len ≤ 64 MB；entry 指向顶层块

# 2. 逐 tick 全等（M3 的正判据，定义见主设计 §7.1）
python simplexc/tools/host/host.py --src simplexc/corpus/rv32im/rv32im.si \
       --bin simplexc/corpus/rv32im/rv32im.bin --entry 0x215B --ticks 10 --out work/tmp/m3/ref.jsonl
python simplexc/tools/host/host.py --src simplexc/corpus/rv32im/rv32im.si \
       --bin work/tmp/m3/rv32im_ours.bin --entry $(cat work/tmp/m3/entry.txt) --ticks 10 \
       --out work/tmp/m3/ours.jsonl
python simplexc/tools/diff_snapshots.py work/tmp/m3/ref.jsonl work/tmp/m3/ours.jsonl
#    期望：10/10 tick 的 pages 哈希 + extern 序列逐条相同，差异 = 0，白名单为空

# 3. 前置基线（先跑，证明宿主本身可靠）
python simplexc/tools/host/selftest.py --entry 0x215B        # 参考 vs 参考 = 0 差异

# 4. 覆盖率与回退率（不许出现 fallback）
python simplexc/tools/check.py --only corpus                  # 现有 4 步仍全过
#    期望：这份源码在 ours 模式下 impl=ours，不 fallback（离线判据就是第 1 步 rc=0）
```

判定标准（什么算过）：
1. **第 0 步 PASS**（代码行 100% 被构造表覆盖，未覆盖 = 0）；
2. **第 1 步 rc=0** 且 blob 头 bit62 = 1、`out_len ≤ 64 MB`、entry 落在机器码范围内；
3. **第 2 步差异 = 0**（不设白名单；10 个 tick 覆盖 `reset_sim` + `mode_refresh` + `mode_run` 三块；
   若 10 tick 不够，逐步加到 100，同一份命令改 `--ticks`）；
4. **第 3 步 = 0 差异**（否则说明是宿主的问题，不是我们的问题）；
5. 同一份源码连编两次 → blob 逐字节相同（装配器已有这条性质，回归用）；
6. 游戏内验证与主频 A/B **不进这条命令**（M4；部署纪律见 facts.md:168 / pitfalls）。

失败怎么定位：差异按 tick 二分（宿主 JSONL 是逐 tick 的），第一处不同 tick 的页地址 → 反查
`mode_refresh` 里对应的 `// <n> com_x` 标记（TSV 的 L2 层 + 组件映射 `facts.md:349` 段）。

## 10. 未定 / 风险

- **未定**：上面 9 条 U-L 实验（TSV 里每条都有配方："最小 `.si` 片段 + 驱动命令 + 观察哪个页/字段"）。
  在它们出结果前，lowering 不该开工（接口 §9 的纪律）。
- **风险 1**：闭包捕获语义（§4c）——错则控制流错，症状是死循环/提前停，不是数值差。
- **风险 2**：非 2 的幂位宽（U5/U33…）在 LLVM 里没有天然的「软件语义」，容易被后端的
  `i33` ABI 假设吃掉；建议在 lowering 里显式掩码。
- **风险 3**：宿主 `simspec` 的地址表缺口（§7.2）——不修的话「逐 tick 全等」这条判据根本跑不起来，
  而且症状（rc=3 / AV）看起来像「我们的产物有问题」，会误导排查方向。
- 次要：`entry` 在产物里的语义仍只知「相对机器码起点的偏移」（facts.md 未定项）；
  我们对它的依赖只是「顶层块编成一个函数、把它的偏移写出去」。
