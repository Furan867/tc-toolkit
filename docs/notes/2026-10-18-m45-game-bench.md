## 结论与交叉核对

1. **新壳在真游戏里跑通了我们的实现**：`impl=ours result=ok`，无 error、无 fallback、游戏不崩。
   旧壳读 blob 的链路被「进程内 `simplexc_compile()`」取代后，第一次在真环境端到端成功。
2. **比 M4 的 `-O0` 原型快 56%，方向与既定预期一致**：`status.md` 记的「C++ 走正确的 `default<O2>`、
   产物小 2.2 倍 → 游戏内更快是待测的」。实测产物 **26404 B vs M4 的 58612 B = 小 2.22 倍**
   （219088/26404），与 `docs/notes/2026-10-18-m45-cli.md:40` 的「COFF 差 2.2 倍」同一因（facts.md:750 的那处枚举值）。
   → 40.375 MHz 不是异常值，是「-O0 原型 → -O2 + 更小产物」的正常结果。
3. 只用了 2 次 `recompile`（#006 reference、#007 ours），撤销栈余量留给后续会话。

## 遗留风险（未验，别当前提）

- **40.375 MHz 只证明「跑得快」，不证明「跑得对」**。逐 tick 等价是差分宿主（M3/M5）的判据，
  这次没跑；真环境里「产物是垃圾但恰好不崩且频率高」在原理上没被这条命令排除。
- 单轮 8 s、7 个采样点、单次会话 —— 40.375 这个绝对值可以被 CPU 状态影响（M4 记过同一产物两次
  4.49/4.29 MHz 的漂移）。要当基线用，需再跑一轮（**得等撤销栈可用**）或多会话复现。
- `spread_pct` 把过渡点算进了分母：小样本下这个字段会高估波动，读报告时看 `samples` 别看它。
