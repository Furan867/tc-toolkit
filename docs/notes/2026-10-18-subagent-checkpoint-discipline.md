# 子 agent 长任务的落盘纪律（2026-10-18）

## 一句话

**派长任务（>10 分钟）时必须在任务卡里写死「先落盘再继续」** —— 否则 30 分钟硬超时会把整轮工作一起带走。

## 证据（同一天内的实测，5 次超时/故障）

| 事件 | 结局 |
| --- | --- |
| `width-cond` 超时 | **报告已落盘**（21:20）→ 结论完整救回；它的实现没落地，但结论是那一轮最有价值的部分 |
| `test-result-chain` 超时 | 代码改动完成、**验证与提交没做** → 靠 resume 拿到结论 |
| `clifail-fixes` 超时 | 三类已提交、报告没写 → 主程存档 patch，让后来者接手 |
| `str-interp` 超时 | 半成品在工作区（能编译、001 能装配）、报告写一半 → 靠 resume 救回 |
| `width-fix`（provider `Connection error`） | 工作区有半成品、无报告 → 主程存档 patch + 回退 |

**规律**：三个真超时里，**两个的损失被「中途落盘」限制在「少了验证步骤」**；只有「报告写一半」那次是真的卡住。

## 纪律写法（直接抄进任务卡）

> 预算 25 分钟；**先落盘再继续** —— 每完成一个阶段就把结论写进 `docs/notes/<你的报告>.md` 一次；
> 接近预算仍未收完就**停下汇报**，别闷头做完再报。

配套三条：

1. **给明确的「阶段」定义**（例如「前端能编译 / lowering 出 IR / 端到端等价 / 扩到全量」）—— 否则「落盘」没有触发点；
2. **要求报告独立可读** —— 它可能就是你唯一拿得到的产物（超时后 transcript 里有，但没人会去翻）；
3. **超时后先查 `docs/notes/` 与 `work/tmp/`**，别默认「什么都没留下」。

## 为什么是 25 分钟

harness 对普通 async 子 agent 的硬超时是 **1800000 ms（30 分钟）**；25 分钟是给它留 5 分钟写盘。

## 反例

- 只说「预算 25 分钟」而不要求落盘 → 超时后只拿到一句半截话（实测：`176/177/180 broke. Bisecting by op group:`）。
- 允许它「最后一起写报告」→ 超时点上正好是最没产出的时刻（验证跑完但没写）。
- 用 `| tail -30` 之类的管道看长任务输出 → 连进度都看不到（本仓 pitfalls 已记；实测两个 worker 又各踩一次）。
