## 0. 结论：规则（可直接变成 `lower.cc` 的改法）

`in_scope(N)` 在引用点 U 为真 ⟺ N 在 U 处可见，分三档：

| 档 | 内容 | 证据 |
| --- | --- | --- |
| ① **预扫**（与 U 的位置无关，也与 `in_scope` 自己的裁剪无关） | `def` · `type`（含 enum 类型名**与成员名**）· 顶层 `const #X`（查询串带不带 `#` 都算）。范围 = **整个编译单元**：顶层 + **程序根语句块（`run_sim:` 的体）的整棵语句树**，块（While/If/`#if`/Switch/label）递归下去；**不钻 `def` 体** | T1 T2 T4 T7 T8 T9 T10 T10b U1 V2 V2b V2c V4 V4b V9a V9b H3 H4 F1 F2 |
| ② **词法**（按出现顺序） | 参数 · 局部 `var`/`let` · 同体（或外层体）里的嵌套 def；**别的 `def` 里声明的嵌套 def 不算**、**别的函数的参数不算** | V6 V8 T5e ✓ / T5 T5d T6 V6b ✗ |
| ③ **前缀** | DLL 内嵌 stdlib 前缀里的 def/type/const 名算（前缀与源码是同一个编译单元） | P1 P2 P3 P3b |

一律为假：完全未定义名（V7）· label 名（V5）· **内建**（`store`/`raw_cast`，P4 P5）·
`var` 声明在引用点**之后**（V1b V1c）· 顶层**不带 `#`** 的 `const`（V3）。

## 1. 方法（判据为什么可信）

1. 参考编译器把 `#if in_scope(…)` / 裸 `if in_scope(…)` 当**编译期常量**：判真的块**内联展开**，
   判假的块**整块不落码**（V7/H2 两个「未定义名」控制片段给的就是这个前提）。
2. 片段里放**唯一 64 位立即数标记**，直接搜产物字节：
   `控制 1111111111111111`（无守卫语句，必须命中）/ `探测 2222222222222222`（被守卫的块）/
   `活着 3333333333333333`（放在 def 体里，用来证明那个 def 真的编进去了，排除 DCE 造成的假「假」）。
3. 每个片段一个子进程（参考编译器遇错 abort 整个进程）。
4. objdump 复核（T7 = 语料形状，判真）：

```text
216a: 48 b9 c7 71 15 b7 8c f2 03 00   movabs $0x3f28cb71571c7,%rcx   ; 控制标记 1111…
2174: 48 89 08                        mov    %rcx,(%rax)            ; store(scratch, …)
2177: 48 b8 08 90 13 5c 5d 02 00 00   movabs $0x25d5c139008,%rax     ; scratch+8
2181: 48 b9 8e e3 2a 6e 19 e5 07 00   movabs $0x7e5196e2ae38e,%rcx   ; 探测标记 2222… ← 守卫块在
218b: 48 89 08                        mov    %rcx,(%rax)
2192: e8 28 ff ff ff                  call   0x20bf
```
   对照 T5d（判假）：入口里只有控制标记与 `call`，**没有**探测标记；而同一份产物里
   活着标记 3333…（0x21ba）在——即被查 def 的体确实编进去了，缺的只是那个守卫块。

## 3. Q2 后置定义 / 两遍还是不动点

- **「含后置定义」只对 ① 档成立**：`def`（T2/H3/H4）、`type`（V4b）、`const #`（V2c）声明在后仍判真；
  但 `var` 声明在后判**假**（V1b/V1c）⇒ 不是「整单元两遍」了事：**① 档走预扫（声明遍），
  var/参数/局部走顺序作用域**。
- **不需要迭代到不动点**：F1（`def` 写在由它**自己**守卫的块里 → 真）与 F2（`def` 写在被
  `in_scope("无此名")` 丢掉的块里，别处查它仍为真）⇒ 名字表取的是**未经 `in_scope` 裁剪的原 AST**，
  一遍预扫就够。
- 两种书写形态同规则：裸 `if in_scope(…)` 与 `#if in_scope(…)` 结果逐条一致（H1/H2 vs T1/V7）。

## 4. Q3 判定范围 = 「前缀 + 源码」一个单元

- 查**只在前缀里定义**的名字（`to_capacity`/`Seed`/`#INT_HIGH`/`INT_HIGH`）→ 全**真**（P1…P3b）。
  前缀是 DLL 里的字面量（`recompile_corpus.py` 从 `stdlib_offset` 抽出来那份），和源码拼成同一个单元。
- 内建名判**假**（P4/P5）⇒ 别把内建表并进名字表；前缀 def 与内建是两张表。
- 对我们的影响：我们只编 `src`（没有前缀），所以**对前缀名的查询我们会判假**。
  98 份语料里没有这种查询（被查的只有 6 个关卡钩子名），属**潜在**缺口；要补最便宜的是把
  `is_prefix_func()` + `prefix_globals()` + `consts_` 并进名字表（各 1 行）。

## 5. Q4 该改什么

现状：`lower.cc:963 in_scope_const()` = `defs_.count(arg->text) != 0`，而 `defs_` 只装
`ast_.defs`（顶层 `FunctionDef`，`lower.cc:2551`）。

**只加「作用域栈」是不够的（必须排除的方案 C）**：语料的形状是「引用点在顶层 `def mode_run` 里，
被查名字是**程序根 while 体**里的嵌套 def」（T7/T8 已验证判真）。两者没有词法包含关系，
而且 `mode_run` 在源码里排在 `run_sim` **前面**（前向）；嵌套 def 的 `Binding::nested`
又绑在**被弹掉的 while 体作用域**里 ⇒ `lookup()` 永远查不到。**真正缺的是 ① 档的整单元预扫。**

| 方案 | 改哪 | 量 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A（推荐）** | 只在 `lower/lower.{hh,cc}`：`Program` 里加 `in_scope_names_` 与 `scan_scope_names()`/`collect_block_names(const Block&)`，`Program` 构造时调；`in_scope_const()` 改成 `名字表 ∪ lookup()` | ~30–40 行 | 只碰 lowering；要手写 5 种语句块的递归（While/If/`#if`/Switch/块），并显式**不钻 `NK::Def` 的体**（这是与「收集所有 def」的关键差别，T5d 是判据） | 
| B | `#if` 裁剪本来按接口冻结版属于**前端**：前端预扫出名字集合，经 `ModuleAst` 传给 lowering | 改前端 + 加 `ModuleAst` 字段 | 改动跨「parser↔lowering」契约（`ast.hh`/`lower.hh` 头注释要求先通知对面写者）；好处是 `#if` 能更早裁掉 | 
| C | `in_scope_const` 里并上 `lookup()` | 2 行 | **不够**（上面那段理由），会给出「修好了」的错觉 | 

方案 A 的骨架（名字表内容按 §2/§3 的表逐条对齐）：

```text
Program::scan_scope_names():                  // scan_decls() 之后
  ast_.defs    → 每个 name                     // 顶层 def
  ast_.enums   → 类型名 + 每个成员名           // V9a/V9b
  ast_.structs → 类型名                        // V4
  ast_.top_vars→ 只收 kw=="const" 且 name[0]=='#' 的（var 不收：V1b/V1c 说 var 顺序敏感）
  ast_.label   → collect_block_names(label->body)
collect_block_names(b):
  NK::Def     → 收名字，**不递归**（T5/T5d：def 体属于那个 def 的作用域）
  NK::While / NK::If / NK::PpIf / NK::Switch → 递归各分支块（含被 in_scope 丢掉的，F1/F2）
  NK::VarDecl → 只收 `const #X`
Lower::in_scope_const():
  names_.count(t) || names_.count(去掉前导 '#') || names_.count('#'+t) || lookup(t) != nullptr
```

未覆盖但已知语义（语料不触发，按「不许留 TODO」的规矩要么补要么写清取舍）：
① 档还要不要收「声明在引用点**之前**的顶层 var」——V1 判真、V1b 判假，判据是**行号比较**
（`st->src_line <= use->src_line`）；② 同体嵌套 def 的前向可见（T5e）。

**判据片段（两边都能编的那份，`O1_two_sided_repro.si`）**——同一份源码，参考编译器与我们的 CLI 各编一次：

## 7. 遗留风险

- **参考编译器自身在两种形状上崩**（`finalize_structured_dag.nim(479,7)`，exit 1）：
  程序根**第一条语句是不带 label 的 `while`**（T3/T12/V1d）。与 U-L14 无关，但说明「while 打头」
  的片段没法用这套方法测；也让 T12/V1d 两条想问的边角落空。
- **顺手发现（不在本任务范围，未改）**：`build_module` 只遍历 `fe.decls`（`depth==0` 的
def/var/const/type/label 四种），**label 之外的顶层语句不进模块**。现象：`T7.ours.bin`（760 B）里
  连控制标记都找不到（同源的 `O1.ours.bin` 把控制语句放进 label 体里就有）。98 份语料里
  **0 份**有这种顶层语句，所以不影响 M5；但它是一条独立于 U-L14 的保真缺口。
- **`var` 的行号语义**没做成片段级闭环（V1/V1b 只有一对前后对照；V1d 崩了）。
  语料不触发，方案 A 里留行号比较即可。
- 顶层 `const x`（无 `#`）判假的原因没查（语料只有 `const #NAME`，V3 只用来划边界）。
- `@Size`/`@Type` 泛型实例化名字与 `in_scope` 的关系**没测**（接口冻结版 U-L14 里提到「`@Size`
  实例化影响」；语料没有这种查询）。
- 前缀名字我们是**判假**的（§4）；只有 6 个关卡钩子名被查，所以当前不影响 98 份。
- 本报告的 40 份归零是**预测**：判据是改完后跑 `coverage.py` 的 98 份差分，不是本文。
