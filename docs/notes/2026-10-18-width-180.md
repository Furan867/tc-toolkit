# 180 的致因行：是**上一轮 patch 的掩码公式写错**，不是「180 里还有别的形状」

2026-10-18。现场 `work/tmp/width180/`：`gate-line.patch`（临时行区间闸）· `fix-shift-amt.patch`（候选改法，**未落地**）·
`gate_{off,on}.ll` · `pt_<行>.ll`（单点验证）· `probe180.py` + `nn_runtime.log` · `head.tsv`（收工态）。
结论在前，证据在后。**代码收工在 HEAD（`0c87efc` 的树），`simplexc/**` 零改动。**

## 0. 结论

1. **致因 = 6 处 U32 移位的移位量掩码，而且是上一轮那两个 patch 自己写错的**：
   `widthfix2/maskonly.patch`（与 `spread-full.patch`）里

   ```c
   uint64_t shift_amt_mask(int bits) { return mask_of(((bits + 7) / 8) * 8 - 1); }
   ```

   `8*ceil(W/8)-1` **本身已经是掩码**（Mersenne 数），再套一层 `mask_of` 就把它当成位宽：
   W=32 时 `31` → `0x7FFFFFFF`。180 里 6 处 `com_lsl`/`com_lsr`（都是 U32）的 `amt` 从这个
   坏 helper 出去变成 `and i64 %amt, 2147483647` —— 越界移位，tick 8 段哈希分叉。
   这也**顺带解释了**上一轮那个「诡异」的观察（`Docs: width-fix2.md` §2）：全铺与只换掩码
   **A/B 哈希一字不差**，因为两个 patch 用的是同一个坏 helper，改的是同一处。
2. 所以「180 里还有别的形状」**不成立**：180 掉的唯一原因就是它。用**修正后**的公式
   （`uint64_t(((bits + 7) / 8) * 8 - 1)`，不再套 `mask_of`）重跑：176/177/180 的 IR
   **逐行相同**（`diff = 0`），一个字节都没变。
3. 也顺带纠正第二处误判：行 3831/8830 **不是** `U1 × U4` 的窄×窄移位 ——
   两个操作数都被 `U32 (...)` 包住了，移位节点上是 `U32 << U32`（掩码 31 两种写法同解）。
   上一版报告把「表达式的内心」当成了「移位节点的类型」。

## 2. 那个形状的参考实测（`probe180.py`，≤3 tick 落盘 · `nn_runtime.log`）

形状 = **窄 × 窄 + 运行期移位量**（上一轮 `shamt`/`shamt2` 全是「窄 × 常量量」，没盖到）。
参考条目：`work/tmp/width180/nn_runtime.{ref,ours}.pages`（`ours` = HEAD 的产物）。

**两条新结论**（都是实测，不是推断）：

| 问题 | 参考给的值 | 说明 |
|---|---|---|
| 结果掩码按谁 | `x1 << x4b(量1)` = **0** · `x2 << x4b(量1)` = **2** | 掩码按**左操作数**的声明位宽（U1 掩 1 位 → 2&1=0；U2 掩 2 位 → 6&3=2）。`unify` 的宽侧（U4）会给 2 / 6 —— 我们错在这里 |
| 运行期移位量按什么取模 | `x7 << x7b(量8)` = **0x7F** · `x6 << x6b(量8)` = **0x3F** · `x9 << x9b(量16)` = **0x1FF** | 量 8/16 被抹成 0 → 按**存储宽度**取模（8&7=0、16&15=0）。硬件的「量取 mod 32」会给 0 / 0 / 0x8000，被否掉 |

其余 15 条（`x1<<x4`=0 · `x4<<x1`=0xA · `x6<<x4`=0x20 · `x7<<x5`=0 · `x5>>x7`=0 · `x12<<x3`=0xF80 ·
`x12>>x3`=0x1F · `x3<<x12`=0 · `x9<<x4`=0x1E0 · `x9<<x12`=0 · `x30<<x7`=0 · `x16<<x3`=0xFF80 ·
`x8<<x8`=0xC0 · `x1>>x4b`=0 · `x2>>x4b`=1）在这一对规则下**全部同解**。

**W ≤ 2 的分歧仍然存在，但这次能被夹死**（`u1` 那条「未解」项拆成两个约束）：

- `x1 << x1`（运行期量 1）参考 **0**：量**没有**被抹成 0（`W-1` 掩码会给 1 —— 那条假设死）。
- `x1 << 2`（常量量）参考 **1**：掩码的第 1 位必须是 0。
- 合起来 U1 的掩码 = **1** = `mask_of(W)`；`x2 << 4` = 3 给 U2 掩码 ∈ {1,3}（同样与「存储宽度 7」相冲）。
- 所以「按存储宽度取模」在 W ≥ 3 上有 8 条判据、在 W ∈ {1,2} 上被否 —— 公式还缺一小块。

## 4. 没落地（代码 = HEAD）

`fix-shift-amt.patch`（把 `uint64_t(bits - 1)` 三处换成 `shift_amt_mask(bits)`）**不许**直接铺，两个理由：

1. 它对 176/177/180 **一个字节都不改**（IR 逐行相同）—— 铺了也拿不到任何判据增量；
2. 规则本身还不完整：§2 的「结果掩码按**左操作数**」我们仍然按 `unify`（宽者胜）算，
   而 W ∈ {1,2} 的移位量掩码与「存储宽度」相冲。这两条都还没被任何一份语料验证过，
   属于**新语义**，得先由负责人定方案。

`widthfix2` 那两个 patch（全铺 / 只换掩码）的差异结论**作废**：它们的判定量是同一个坏 helper
造出来的。
