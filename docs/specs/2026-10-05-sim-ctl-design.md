# 设计：仿真控制工具 simctl

- 日期：2026-10-05（2026-10-06 重写 `recompile` 一节：进程内调用路线废弃，改用 UI 事件注入）
- 分支：`feat/sim-ctl`
- 状态：`run`/`stop` 已实测可用；`recompile` 机制已实测打通，待写实现计划

## 目标

让外部脚本能脚本化这一循环：**改 opt.ini → 重编译 → 运行 → 停止 → 再改**。
本工具只负责其中「重编译 / 运行 / 停止」三个动作，供其他脚本调用。

## 接口

核心模块 `tools/simctl.py`，暴露三个函数：

```python
simctl.run()         # 启动电路运行
simctl.stop()        # 停止电路运行
simctl.recompile()   # 触发一次重编译
```

- 三者都返回结构化结果（成功/失败 + 原因），失败给原因
- 内部缓存进程句柄；PID 或模块基址变化时自动重查（游戏重启、Steam 更新后地址位移）
- 另附同名 CLI 薄壳，供手工敲或其他语言调用（`import` 比每次起解释器快，这是留函数接口的原因）

## 行为契约

### `run`

写四个字段：

| 字段 | 值 |
| --- | --- |
| `settings[1]` sim_target_cycle | `INT64_MAX` |
| `commands[0]` ctl_command | `0` (run) |
| `commands[1]` ctl_command_id | 新 id |
| `simulation_next_command_id` | 新 id + 1 |

判据：`set[0]` (sim_cycle) 递增。**已实测** —— 1 秒后电路跑起来，读到 10.75 MHz。

### `stop`

写 `commands[0] = 3` (quit_simulation) + 新 id。

判据：`set[14]` (sim_running) == 0 且 `set[0]` 为哨兵。

> 说明：`3` 是「停止」按钮与「编辑电路时自动停止」共用的命令（实测日志 40.1s）。
> `2` (mode_reset) 是「暂停」，语义不同，本工具不用。

### `recompile`

**机制：UI 事件注入。** 不去调用游戏内部函数，而是注入按键，让游戏自己走
「电路变化 → 重建场景 → 编译」那条路。

固定序列，无分支：

```text
1. 抢游戏窗口到前台（AttachThreadInput + 先模拟一次 Alt 解锁前台限制）
2. 校验前台确实是游戏 —— 不是则中止，绝不发键
3. SendInput 发 Ctrl+Z      （撤销）
4. SendInput 发 Ctrl+Shift+Z（重做）
5. 返回「按键已发出」，不判断编译是否成功
```

**为什么成对发「撤销 + 重做」**：

- 撤销与重做**各触发一次重建 + 编译**，效果等价
- 成对发送后**净效果为零** —— 电路回到原样，不会打乱用户的编辑
- 避免跨调用记忆「上次发的是哪个」：若连续两次只发 Ctrl+Z，第二次无操作可撤销，就不会触发

实测：一次 Ctrl+Z 或一次 Ctrl+Shift+Z，`next_sim_version` 都 **+3**（游戏内部固定发 3 次编译请求）。

### 不做的事（设计原则）

- **不做自动检测**：不监听 opt.ini 的 mtime、不做任何"发现变化就自动重编译"。重编译一律由外部**主动调用**触达。
- **不判断编译是否成功**：编译成功必然经过 `compile.dll`；调试靠转发层日志或主频工具，工具本身不另加判据，徒增复杂度。
- **不改 opt.ini**，不做计时，recompile 后不自动 `run`。

## 前提与调用者责任

| 前提 | 说明 |
| --- | --- |
| 游戏在运行 | 否则返回失败 |
| 电路**有可撤销的编辑历史** | 否则 Ctrl+Z 无事可做 → 不会触发。调用者需保证电路刚被编辑过（例如加一根线） |
| **处于电路编辑模式** | 不是运行模拟时 |
| **重编译期间前台会被抢走** | 用户会短暂失去焦点，这是本方案的代价 |

## 抢前台

`SetForegroundWindow` 从后台进程调用**会被前台锁拒绝**（表现只是任务栏图标闪一下）。
实测：agent 启动的 python、前台是 VS Code 时，直接调用返回 `False`。

有效手段（已实测两次成功）：

1. 先 `SendInput` 发一次 **Alt 键**（`VK_MENU` 按下+抬起）—— 系统会放宽前台限制
2. `AttachThreadInput(本线程, 前台线程, TRUE)` 把自己的输入队列接到前台线程
3. `BringWindowToTop` + `SetForegroundWindow`
4. 之后 `AttachThreadInput(..., FALSE)` 解除

**安全铁律**：发键前必须校验 `GetForegroundWindow() == 游戏窗口`。
`SendInput` 把键发给**当前前台窗口**，抢前台失败时若仍发键，**会把 Ctrl+Z 打到别人的程序上**
（实测中真的误发给了 VS Code）。校验不通过 → 中止并报错，绝不发键。

## 并发约定

`simctl` 的每个动作同一时刻只允许一个在执行，内部用一把文件锁串行化，跨进程有效。
并发调用排队等待，而不是交错执行 —— 否则两次 `recompile` 的按键会交错，状态不可预期。

## 实测记录（2026-10-06）

| 方式 | 结果 |
| --- | --- |
| `PostMessage`（投递 `WM_KEYDOWN`，不需要前台） | ❌ **不通**。窗口是 GLFW 的，投递的按键（含修正 scan code 后）游戏不响应，`next_sim_version` 不变 |
| `SendInput` + 抢前台 | ✅ **可用**。两次连测（前台起点均为 VS Code）：`119 → 122`（undo）、`122 → 125`（redo） |

判据用 `next_sim_version`（`.data 0x14049c300`）：每次编译请求 +1，**纯读内存，不需要转发层**。

## 风险

- 写内存与抢前台都可能扰动用户的桌面状态；用户已接受
- 所有地址依赖进程实例，游戏重启即失效（工具自动重查）
- Steam 更新会让函数地址位移，需重新确认
- 若游戏更新改了撤销/重做的快捷键，本机制失效
